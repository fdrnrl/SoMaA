# Журнал решений

Формат: дата — решение — причина.

## 27.10.2026

- **Спецификация лежит в docs/spec.md.** Причина: одна версия требований для всей команды и для ИИ-агента.
- **В requirements.txt закреплены точные версии прямых зависимостей; numpy 2.1.3.** Причина: scipy 1.14.x не поддерживает numpy новее 2.2; pandas 2.2.3 работает с numpy 2.1.
- **Dockerfile ставит postgresql-client-16 из репозитория PGDG.** Причина: в Debian bookworm есть только клиент 15, а pg_dump должен совпадать по основной версии с сервером postgres:16.4.
- **В M0 docker-compose содержит только db; migrate появится в M1 вместе с db/migrate.py.** Причина: не держать сервис, которому нечего запускать.
- **Порт базы открыт только на 127.0.0.1:5432.** Причина: тесты и DBeaver на этом компьютере подключаются к базе, а из сети она недоступна.
- **Тесты и линтер запускаются из локального окружения .venv (make install).** Причина: быстрее, чем пересобирать образ на каждый запуск.
- **В CI база PostgreSQL работает без пароля (POSTGRES_HOST_AUTH_METHOD=trust).** Причина: база временная и живет только во время задания CI; так в репозитории нет паролей (NFR-06).
- **ruff проверяет правило DTZ.** Причина: автоматически ловит naive datetime (раздел 4.2).
- **Настройки ruff и pytest — в pyproject.toml.** Причина: один файл для настроек инструментов; в разделе 5 он не указан, но и не запрещен.

## 28.10.2026 (M1)

- **Внешних ключей на справочники в core нет (sessions → schools, regions, subjects).** Причина: справочники могут прийти позже фактов, и загрузка не должна падать (раздел 7.2); ссылочная целостность проверяется в Q-CONS-07.
- **Внешние ключи load_id → ops.load_log добавляются в 003_ops.sql через ALTER TABLE.** Причина: таблицы core создаются в 002, а ops.load_log — только в 003.
- **В ops.load_log добавлен статус running (кроме ok, error, partial).** Причина: строки core ссылаются на load_id уже во время загрузки, поэтому строка журнала создается в начале запроса и обновляется в конце.
- **У справочников core и core.live_status тоже есть loaded_at и load_id.** Причина: единообразно с остальными таблицами core (раздел 7.2, служебные столбцы).
- **Столбец NOT NULL, если в контракте у поля «null: нет».** Причина: в базу попадают только записи, прошедшие проверку, а NOT NULL — вторая линия защиты.
- **Роли sma_loader, sma_reader, sma_app создает db/migrate.py, а не SQL-файл.** Причина: пароли берутся из .env и не должны лежать в репозитории. Если пароль не задан (CI), роль создается без пароля, и войти по паролю под ней нельзя.
- **Права на таблицы выдаются через ALTER DEFAULT PRIVILEGES в 001_schemas.sql.** Причина: новые таблицы автоматически получают нужные права, и их не забудешь выдать.
- **Обновлять материализованные витрины может только их владелец.** Решение на M5: функция mart.refresh_all() с SECURITY DEFINER, право EXECUTE — у sma_loader.
- **Добавлен модуль sma/db.py (подключение к базе по переменным окружения).** Причина: одно место для настроек подключения у migrate.py, тестов и загрузчика.
- **При локальном запуске SMA_DB_HOST=localhost задает Makefile.** Причина: в .env стоит db (адрес внутри Docker); переменные окружения важнее .env, поэтому CI может задать свой адрес.
- **Пока база есть только у разработчика, миграции можно править и пересоздавать базу (make db-reset).** После того как базой начнут пользоваться другие, примененные файлы не меняются: каждое изменение — новый файл миграции.
- **Контракт в sma/contract.py — список объектов Field для каждого адреса; блоки экзаменов и /live-status описаны отдельно.** Причина: у блоков особое правило (ровно один блок по exam_type), а у /live-status нет служебных полей.
- **В SQL — только CHECK на один столбец (перечисления и диапазоны из контракта). Правила, сравнивающие два столбца (score ≤ max_score), проверяет валидатор (M3) и качество данных.** Причина: при ошибке CHECK отменяется вся страница из 1000 записей, и загрузчик застревает на ней; запись, не прошедшую проверку в Python, можно отклонить одну. score > max_score валидатор отклоняет с reason_code out_of_range (это правило контракта 6.5, а не согласованность состояний из 6.12).

## 31.10.2026 (M2)

- **normalize_answer (sma/normalize.py) делается на этапе M2, а не M3.** Причина: генератор определяет is_correct по нормализованному сравнению (раздел 10.5).
- **M2 умеет один снимок — after_check; record_id уже сейчас UUID5 от естественного ключа.** Причина: timeline, апелляции и остальные снимки — этап M6; детерминированные record_id нужны уже для повторной загрузки в M3.
- **Сборка записей вынесена в модуль sma/generator/records.py (в разделе 5 его нет).** Причина: generate.py остается коротким — только порядок шагов и запись файлов.
- **Число не явившихся и аннулированных — ровно round(доля × N), участники выбираются случайно.** Причина: в маленьком наборе случайное число могло бы оказаться нулем, и тесты состояний ничего бы не проверяли.
- **Участники делятся по школам ровно на participants_per_exam (split_sizes); в профиль добавлен ключ schools.used_count.** Причина: test_generator_counts требует точного совпадения с параметрами.
- **Время на часть 1 — половина рабочего времени самого ученика, распределенная по Дирихле.** Причина: «половина длительности экзамена» не помещается в работу ученика, который сдал на 55% длительности.
- **Каждый файл набора — страница ответа API {"page", "total_pages", "items"}; записи отсортированы по (updated_at, record_id).** Причина: FileSource (M3) читает файлы так же, как ответы API.
- **absent и annulled: result_status = final, все значения блока экзамена — null.** Причина: итог не изменится, а результата по шкале нет (6.12).
- **block_failed = (баллы по геометрии < 2).** Причина: в условной шкале ОГЭ минимум задан только для геометрии.
- **В manifest.json нет времени создания набора.** Причина: иначе два запуска с одним seed дают разные файлы (NFR-23).

## 08.11.2026 (M3)

- **Отклоненная запись — одна строка в ops.rejected_records: reason_code и field — первой проблемы, в message — все проблемы.** Причина: по одной записи легко найти причину и record_id (T-03), а полный список не теряется.
- **Удаленные записи (deleted = true) справочников regions, schools, subjects не применяются и считаются в skipped_stale.** Причина: эти справочники общие для всех платформ, столбца deleted в них нет (раздел 7.3).
- **Дубли одной записи внутри страницы схлопываются до версии с наибольшим updated_at до записи в базу; лишние считаются в skipped_stale.** Причина: один INSERT ... ON CONFLICT не может изменить строку дважды.
- **Водяной знак только растет (GREATEST в SQL) и не ставится, если на адресе нет ни одной записи.** Причина: перекрытие since может вернуть только старые записи, и знак не должен откатиться назад; при пустом адресе следующий цикл просто снова спросит все.
- **Запись с неразборчивым updated_at FileSource не отфильтровывает по since, а передает на проверку.** Причина: ее должна отклонить проверка и записать в журнал, а не молча потерять фильтр.
- **Загрузчик (run.py) подключается под ролью sma_loader.** Причина: принцип наименьших прав (раздел 7.1); тест test_loader_role_has_enough_rights проверяет, что прав хватает на весь цикл.
- **Разные синтетические наборы нельзя грузить в одну базу подряд: у них одинаковое время экзамена, и водяные знаки первого набора отсекают записи второго.** Перед загрузкой другого набора — make db-reset.
- **В M3 run.py умеет только --once; планировщик и ApiSource — этап M4.**
- **make up: сначала база с --wait, затем migrate через docker compose run.** Причина: --wait считает завершившийся сервис migrate (даже с кодом 0) ошибкой.
